# Development approach

This document covers both repositories: the Expo app
([wide-impact-joinly-mobile](https://github.com/ammarelgml/wide-impact-joinly-mobile)) and this API.

## How I approached the task

1. **Specify before coding.** The features are small, so the review is about decisions. I wrote a
   short product and technical spec first and answered every question the brief leaves open
   ([decisions.md](decisions.md)): who signs in, what a code looks like, how long it lives, what
   happens on a double tap, what a student may see.
2. **Backend first, against a real database.** The API was built, tested and deployed first. The
   mobile app is built against the deployed API, not mocks, so the error codes and edge cases are
   settled before any screen depends on them.
3. **Rules in the database, then in one service.** Constraints that must never break (role
   ownership, one enrollment, one live code, no code collisions) are SQL constraints. Business
   rules live only in services. Then the tests try to break both.
4. **Mobile: flows first, then design.** I built every teacher and student flow with loading, empty,
   error and offline states, then applied a design handoff (tokens, type, components) on top, then
   tested every flow on an Android emulator and fixed what that found.
5. **Deliverables as code.** API docs, OpenAPI and the written reference are generated from the
   same definitions the server enforces; CI fails if the written reference is stale, and the app's
   CI fails if the deployed API's contract no longer matches the app.

## Architecture

```
Expo app ──HTTPS/JSON──▶ Express API ──SQL (pg pool)──▶ PostgreSQL
  │                        │
  │ Google Sign-In          ├─ route: auth + role + zod validation (from endpoints.ts)
  │ (native) ─ID token─▶    ├─ controller: maps input to a service call
  │                        ├─ service: business rules, transactions
  │                        └─ repository: SQL only (Kysely)
  ◀── access JWT (15 min) + rotating refresh token (30 days)
```

### Mobile app

- **Structure by feature.** `src/app/` holds only routes (Expo Router, file-based); each route
  re-exports a screen from `src/features/{auth,classrooms,enrollments,join}`. Shared UI lives in
  `src/ui/` and is built from the design tokens in `src/ui/theme.ts`.
- **Role-based navigation.** The root layout restores the session and uses `Stack.Protected` guards,
  so a teacher can never reach the student stack or the reverse, and a signed-out user only sees the
  welcome and role screens.
- **State management, split by kind of state.** Server data (classrooms, roster, enrollments) lives
  in TanStack Query: caching, pull to refresh, optimistic updates, retries only for network and 5xx
  errors, and polling only while a live screen is open (invite every 2 s, classroom every 5 s).
  The only client state is the session, in a small zustand store. Forms use react-hook-form with
  zod schemas whose limits match the API (a test checks them against the contract).
- **Typed API client.** `openapi-fetch` with types generated by `openapi-typescript` from the API's
  `/openapi.json`. A wrong path, parameter or body is a compile error. Screens branch on the stable
  error `code`, never on message text, and `src/api/messages.ts` maps each code to one sentence
  that says what to do next.
- **Device features.** `expo-camera` for scanning, `react-native-qrcode-svg` for showing the QR,
  `react-native-view-shot` and `expo-sharing` to share the QR as an image (WhatsApp or any app),
  and on the invite screen keep-awake, full brightness and a landscape layout.

### API

- **Endpoints as data.** Each module declares its endpoints in `endpoints.ts`: method, path,
  role, zod schemas for params, query, body and each response, and the error codes it can return.
  `mount()` turns a declaration into a route (authentication, role check, validation), and the
  handler's return type is checked against the declared responses at compile time. Outside
  production every response is also validated against its schema at runtime, so a contract
  violation fails the tests instead of reaching the app.
- **One contract for the app.** The OpenAPI 3.1 document at `/openapi.json` is generated from those
  declarations. The mobile app generates its TypeScript client types from it, so the two
  repositories cannot silently disagree.
- **Errors.** Services throw `AppError(code)`; one middleware renders RFC 9457 problem details with
  a stable `code`, the request id, field errors for validation, and `Retry-After` for rate limits.
  Unknown errors are logged with the request id and returned as a generic `INTERNAL`.
- **Testability.** The Google verifier and the clock are injected interfaces. Tests run without
  Google and move time forward to test 24-hour code expiry and 15-minute token expiry.

## How the app, API and database communicate

1. The app signs in with Google natively and receives a Google **ID token** whose audience is our
   Web client ID.
2. It posts the ID token to `POST /v1/auth/google`. The API verifies it with Google's public keys
   and checks audience, issuer, expiry and verified email. A new user gets `422 ROLE_REQUIRED`;
   the app asks Teacher or Student and resends the same token with `role`.
3. The API returns its own **access token** (JWT, 15 minutes, kept in memory on the device) and a
   **refresh token** (opaque, 30 days, stored in the Android Keystore via `expo-secure-store`).
   Google tokens never authorise API calls.
4. Every request carries `Authorization: Bearer <access token>`. On `401 TOKEN_EXPIRED` the app runs
   one shared refresh and retries once. Refresh rotates the token; reusing an old one revokes the
   session.
5. **Joining.** The QR encodes `https://<api>/join?code=NNNNNN`. On Android with Joinly installed,
   that link opens the app (a verified App Link: the API serves `/.well-known/assetlinks.json`); on
   any other phone it opens a small page with the code and a download link. A scanned QR, a link
   opened by the camera app and a typed code all go to `POST /v1/enrollments/preview` (the student
   sees the class first), then `POST /v1/enrollments`.
6. The API talks to PostgreSQL through a connection pool. Multi-step writes (create a classroom with
   its first code, regenerate a code, rotate a refresh token) run in transactions, with row locks
   where two requests could race.

## Challenges and how I resolved them

- **Concurrent joins.** Ten simultaneous taps must produce one enrollment and ten successes. A
  composite primary key plus `INSERT … ON CONFLICT DO NOTHING RETURNING` gives exactly that without
  locks; the test fires ten parallel requests.
- **Code collisions inside a transaction.** A unique violation aborts a Postgres transaction, so a
  naive retry fails. The insert uses `ON CONFLICT DO NOTHING` and retries with a fresh number when no
  row comes back; expired codes are swept first so their numbers are reusable.
- **"Expired" vs. "invalid".** If expired codes were simply deleted, a student would be told the code
  is wrong when it is just old. Keeping code history, with a revoke reason, lets the API answer each
  case precisely without letting old codes count as valid.
- **Role safety beyond middleware.** A bug in a route guard should not let a student own a class.
  `users` has a unique `(id, role)` and the foreign keys reference it with a fixed role, so the
  database rejects it.
- **Two repositories, one contract.** Without a shared package, drift is the risk. Generating
  OpenAPI from the enforced schemas, validating responses in tests, and generating the app's types
  from `/openapi.json` makes drift a build failure instead of a runtime bug.
- **Parallel token refreshes.** With rotating refresh tokens, two screens refreshing at once would
  present the same token twice, which the API treats as theft. The app wraps refresh in a
  single-flight helper, so concurrent requests share one refresh; tests cover it.
- **A QR scanned by a phone without the app.** A custom `joinly://` link does nothing on such a phone.
  Switching the QR to an https link with Android App Links means the same QR opens the app when it is
  installed and a download page when it is not. Scanned data is untrusted, so the app accepts only
  that https form on the API's own host (and the older `joinly://` form), with one 6-digit code.
- **Opening a join link while signed out.** The code is kept in the session store through sign-in
  and role choice, and the student lands on the join confirm. A link opened from a cold start still
  has a way back, because each role stack starts from its home screen.
- **Android crash after changing font size.** Android recreated the activity and Expo Router's
  router never became ready again, so the next tap crashed. A small config plugin
  (`plugins/with-android-config-changes.js`) lets the activity handle font, display size and
  language changes in place.
- **Google sign-in in review builds.** Native Google sign-in needs an Android OAuth client matching
  the signing key, and reviewers may not have a suitable account or device. A flag-gated demo
  sign-in with seeded accounts keeps every flow testable.

## Assumptions and compromises

- One role per account, chosen at first sign-in.
- Single API instance, so in-memory rate limiting is sufficient (behind an interface for Redis later).
- Live updates by polling while a screen is open, rather than WebSockets.
- Android APK only; the code is cross-platform but no iOS build was made in the time box.
- Demo sign-in is enabled on the review deployment only, so reviewers are not blocked by Google's
  device checks.
- Light theme and English only, although the design tokens already include a dark palette and the
  layouts use start/end for right-to-left.

## What I would improve with more time

- Shared rate-limit store and a grace window for refresh token rotation.
- Server-sent events for the live roster instead of polling.
- An iOS build, dark theme and Arabic (right-to-left).
- Offline queueing for writes; reads already work from cache.
- Audit log of membership changes (who joined, who was removed, by whom).
- Account deletion endpoint and data export.
- Co-teachers (a `classroom_teachers` table) and role changes by an admin.
- Load test of the join path and a Postgres-backed limiter for multi-instance deployments.
